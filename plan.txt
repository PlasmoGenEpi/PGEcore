Convert the PGEcore repository into a standard R package while preserving its existing purpose and CLI behaviour.

## Goal

PGEcore is shared across multiple Nextflow and WDL pipelines. It contains R scripts that either implement shared functionality or wrap external bioinformatics/statistical tools.

We currently include PGEcore in pipelines as a Git submodule. We want to replace this with a versioned R package that can eventually be distributed through Conda (and potentially CRAN).

**Important:** PGEcore must NOT install all of the external tools that it wraps. Those tools will continue to be installed separately in the Conda environment for each pipeline process.

For example, a Nextflow process should eventually be able to have an environment containing:

```text
r-pgecore
tool-a
```

while another has:

```text
r-pgecore
tool-b
```

Installing PGEcore itself must not cause tool-a, tool-b, etc. to be installed.

## First: audit the repository

Before making changes:

1. Inspect every current script/module in PGEcore.
2. Identify:

   * reusable R code
   * CLI argument parsing
   * external-tool invocation
   * R package dependencies
   * external executable dependencies
   * shared utility functions
3. Produce a short migration plan mapping every existing script to its proposed package location.
4. Identify anything that does not fit cleanly into the proposed structure before modifying it.

Do not remove functionality just to make something fit the package structure.

## Target structure

Move toward a conventional R package structure such as:

```text
PGEcore/
├── DESCRIPTION
├── NAMESPACE
├── LICENSE
├── README.md
├── NEWS.md
├── R/
│   ├── tool_a.R
│   ├── tool_b.R
│   ├── utilities.R
│   └── ...
├── inst/
│   └── scripts/
│       ├── tool_a.R
│       ├── tool_b.R
│       └── ...
├── man/
├── tests/
│   ├── testthat.R
│   └── testthat/
├── vignettes/
└─ CLI

For each existing script, move the actual implementation into functions under `R/`.

For example, conceptually change:

```text
script
├── parse CLI arguments
├── validate input
├── prepare input
├── run tool
└── process output
```

into:

```text
R/tool.R
├── validation functions
├── input preparation
├── run_tool()
└── output processing

inst/scripts/tool.R
└── CLI parsing + call PGEcore::run_tool()
```

The scripts under `inst/scripts/` should be deliberately thin.

Where practical, preserve the existing CLI arguments and behaviour so existing Nextflow/WDL processes require minimal changes.

Do not duplicate implementation between `R/` and `inst/scripts/`.

## External tools

External executables must NOT become R package dependencies.

For wrappers around external programs, add a shared internal helper for checking executables, e.g.:

```r
check_external_tool <- function(tool) {
    path <- Sys.which(tool)

    if (path == "") {
        s'%s' to be installed and available on PATH.",
                tool
            ),
            call. = FALSE
        )
    }

    invisible(path)
}
```

Use this consistently before invoking external programs.

Document the external executable required by each wrapper.

Do not attempt to download or install external tools from PGEcore.

## R dependencies

Audit the R dependencies carefully.

Packages genuinely required by most/all PGEcore functionality can go in `Imports`.

Do not automatically make every R package used by one specialised wrapper a mandatory dependency.

Where appropriate, make specialised dependencies optional and check them at runtime with `requireNamespace()`.

Avoid `library()` calls inside package implementation code. Prefer qualified calls such as:

```r
package::function()
```

The goal is to avoid making installation of PGEcore pull in a huge collection of unrelated dependencies where that is unnecessary.

## Public API

Decide which functions should form the supported public API and mark only those with `@export`.

For example, high-level functions such as:

```r
PGEcore::estimate_prevalence(...)
PGEcore::translate_variants(...)
PGEcore::run_some_tool(...)
```

may be public.

Low-level parsing, validation and formatting helpers should normally remain internal.

Document every exported function with roxygen2.

## CLI interface

PGEcore must continue to support command-line use because the same functionality is used from:

* Nextflow/nf-core
* WDL/Terra
* shell scripts
* direct R use

The package therefore has two supported interfaces:

```text
PGEcore
├── R API
│   └── PGEcore::function()
└── CLI
    └── packaged scripts
```

Ensure packaged CLI scripts can reliably locate/use the installed PGEcore package.

If there is a cleaner standard R-package mechanism for installing executable scripts than `inst/scripts/`, investigate it and explain the trade-offs before changing the proposed design.

## Testing

Introduce `testthat`.

Separate tests into:

### Unit tests

These must not require external tools where possible. Test things such as:

* argument/input validation
* input parsing
* input formatting
* command construction
* output parsing
* output formatting
* pure R algorithms
* shared utilities

### Integration tests

Tests that actually invoke external tools should:

* detect whether the executable is available
* skip cleanly if it is unavailable
* run in our own CI environments where the relevant external tool is installed

The package should be capable of passing `R CMD check` without every external tool being installed.

Do not hide genuine package errors by broadly skipping tests.

## Documentation

Rewrite the README to explain the architecture clearly.

Near the beginning, explicitly state:

> PGEcore does not install or distribute the external software that it wraps. External tools must be installed separately and available on PATH. This allows workflow processes to install only the software required for that process.

Document the two ways of using Plibrary(PGEcore)

result <- some_function(...)
```

### From a workflow/CLI

Show how an installed CLI script is invoked.

Also create documentation summarising external dependencies, ideally as a table containing:

| PGEcore function/script | External tool | Tested version | Notes |
| ----------------------- | ------------- | -------------- | ----- |

Clearly distinguish:

* R package dependencies
* optional R dependencies
* external executable/runtime dependencies

Add a contributor/developer section explaining how a new wrapper should be added.

## Conda compatibility

The package will eventually be distributed as `r-pgecore` through an appropriate Conda channel.

Design the package so that a Nextflow process can have an environment conceptually like:

```yaml
dependencies:
  - r-base
  - r-pgecore
  - external-tool-required-by-this-process
```

Another process should be able to install a different external tool without PGEcore pulling in the first one.

Do not create a single environment containing every tool PGEcore supports.

## CRAN compatibility

Where reasonable, follow normal R package and CRAN conventions so that future CRAN submission remains possible.

In particular:

* `R CMD check` should work without all external executables installed
* external-tool integration tests should skip when appropriate
* do not download/install external software during package installation
* use standard DESCRIPTION dependency fields correctly
* document system/external requirements clearly

Do not make compromises solely for CRAN if they would make the package unsuitable for our Nextflow/WDL use case. Conda/workflow use is the primary requirement.

## Backwards compatibility

Avoid changing the computational behaviour of existing scripts during this migration.

Where practical:

* preserve CLI option names
* preserve input formats
* preserve output formats and filenames
* preserve defaults

If something must change, document it explicitly rather than silently changing behaviour.

## Implementation approach

Do this incrementally rather than rewriting everything at once.

1. Audit the existing repository and present the proposed mapping.
2. Create the basic R package skeleton.
3. Migrate shared utility functions.
4. Migrate one simple/pure-R script as a proof of concept.
5. Migrate one wrapper around an external executable as a proof of concept.
6. Add tests for both.
7. Run `R CMD check`.
8. Once the pattern is working, migrate the remaining scripts one by one.
9. Update documentation.
10. Run the existing tests as well as the new package tests and report any behaviour changes.

Before making large or destructive changes, show me the proposed structure and migration mapping so I can review it.

The end result should be a normal, versioned R package that provides the same shared functionality as the current PGEcore repository, can be used directly from R or from command-line workflows, and **does not bundle or install the external tools that individual wrappers call**.
